# OpenGLESScope Database 3.0.29 — cache release recovery audit

## Incident
The 3.0.28 local source quality gate reported CHANGES REQUIRED because obsolete v3027 assets and transient Worker directories were still present in the existing checkout. Deployment nevertheless continued. A failed source gate prevents the Pages publication workflow from producing the matching release/snapshot, so advancing the Worker can leave Worker and Pages on different Database releases. That release mismatch breaks the intended cache-first publication handshake even though the cache loader itself was not changed.

## Cache preservation
`app.v3029.js`, after normalizing only the Database version literal from 3.0.29 to 3.0.27, must match the exact SHA-256 of the shipped 3.0.27 application asset. Therefore preload manifest validation, cached chunk integrity verification, cache-first rendering, incremental live reconciliation and bounded detail GET behavior are unchanged.

## Network banner preservation
The 3.0.28 fix remains isolated to the experience/banner presentation layer and shared CSS geometry. Verified cache startup does not count as a network interruption. Real offline/API interruption still drives offline/checking/restored state.

## Release preflight
When replacing files inside an existing checkout, run repository repair before the quality gate. A non-zero quality-gate exit is terminal: do not deploy Worker and do not push that release. Worker and Pages must advance as one matching release generation, and Pages publication must include the complete SHA-256 verified preload.

## Immutable contracts
No D1 migration, producer-floor change, schema/technicalReport/normalizer change, public preload format change, report rewrite, GL/EGL evidence change, privacy relaxation or security relaxation is part of 3.0.29.
